# What to upload, and where

One folder per Play Console upload box. Everything in here is generated by
`tools/build-store-assets.sh` — **do not hand-edit these files**, edit the script or the
raw captures and re-run it.

Play Console → **Grow users → Store presence → Store listings → Default store listing**.

| Folder | Play Console field | Files | Size |
|---|---|---|---|
| `app-icon/` | App icon | `icon-512.png` | 512 × 512 |
| `feature-graphic/` | Feature graphic | `feature-graphic-1024.png` | 1024 × 500 |
| `phone/` | Phone screenshots | 5 files, upload all, in filename order | 1080 × 1920 |
| `wear-os/` | Wear OS screenshots | 2 files | 454 × 454 |
| `tablet-7in/` | 7-inch tablet screenshots | **empty on purpose** | — |
| `tablet-10in/` | 10-inch tablet screenshots | **empty on purpose** | — |
| `chromebook/` | Chromebook screenshots | **empty on purpose** | — |

The Wear OS box only appears once the Wear form factor has been added to the app, which
happens at release time. If the tab is not there yet, upload everything else and come back.

---

## Why three folders are deliberately empty

Play marks the tablet and Chromebook boxes with an asterisk, but read the error text
underneath: *"Upload at least 2 phone or tablet screenshots."* It is **one** requirement
shared across all of them, and the five phone screenshots satisfy it. The tablet and
Chromebook boxes are genuinely optional.

They are empty because **SajdaTime has no tablet layout yet**. Dropping the phone captures
into the tablet slots would show a stretched phone UI and advertise a tablet experience
that does not exist. The only cost of leaving them blank is that Play will not surface the
app in tablet and Chromebook recommendations, which is the correct outcome until there is
a real large-screen layout.

Fill these in when that layout exists, and not before.

---

## Aspect ratio is the trap

Play accepts phone screenshots at **16:9 or 9:16 and nothing in between** — that is the
Console's own wording, not an inference. A modern phone is 20:9, so a native capture off a
current device is *automatically rejected*.

This bit was wrong once. The captures came off a Pixel 7 AVD at 1080 × 2400 (2.22:1) and
were scaled down onto a 9:16 canvas, pillarboxed in brand green. That complied, but it
threw away a fifth of the frame, shrank the UI, and wrapped a green surround around an app
that never draws one.

They are now captured **natively at 1080 × 1920** and copied through untouched.

## Retaking the captures

The AVD matters, so it is scripted rather than described:

```bash
# 9:16 at 420dpi, and — the part that is easy to miss — no display cutout.
# A Pixel 7 profile forces a hole-punch whose 136px inset does not fit a 1920-tall
# screen and clips the status bar clock in half.
avdmanager create avd -n sajdastore \
  -k "system-images;android-36;google_apis;arm64-v8a" -d pixel_2 --force
```

Then, with the app installed:

```bash
adb emu geo fix -2.2426 53.4808          # Greater Manchester
adb shell pm grant com.sajdatime.app android.permission.ACCESS_COARSE_LOCATION
adb shell cmd appops set com.sajdatime.app SCHEDULE_EXACT_ALARM allow

# A clean, consistent status bar. This is system chrome only — no app pixel is touched.
adb shell settings put global sysui_demo_allowed 1
adb shell am broadcast -a com.android.systemui.demo -e command enter
adb shell am broadcast -a com.android.systemui.demo -e command clock -e hhmm 1200
adb shell am broadcast -a com.android.systemui.demo -e command battery -e level 100 -e plugged false
adb shell am broadcast -a com.android.systemui.demo -e command notifications -e visible false
```

Two things that are not obvious:

- **`geo fix` expires.** The app will sit on "Finding your location…" if you send it once
  and wait. Send it repeatedly until the city name resolves.
- **Grant `SCHEDULE_EXACT_ALARM` before capturing**, or the Times screen carries the amber
  "the system is withholding this" banner. The banner is honest and should stay in the app;
  it just is not what the screenshot is there to show.

### The compass needs feeding

An emulator has no magnetometer, so the Qibla screen reads *"You are facing 0°"* — which is
what the previous store screenshot showed, and it is not a state any real user sees. Set
the sensors by hand:

```bash
adb emu sensor set acceleration 0:0:9.81        # flat, screen up
adb emu sensor set magnetic-field -17.3:10:-45  # heading 60°, northern-hemisphere dip
```

That yields "You are facing 60°" against a Qibla of 118°, and the app correctly says
*"Turn right 58°"*. Checking that 118 − 60 = 58 in the captured image is a free end-to-end
test of the compass maths, so it is worth doing every time.

### Wear OS

Captured from the `sajdawear_large` AVD at 454 × 454 (Play wants 1:1, minimum 384). The
watch is a **horizontal pager**: the Qibla is one swipe left from the times list, not a
separate activity.

The watch AVD has no magnetometer either, and unlike the phone there is no sensor value
that fakes one convincingly — so the watch Qibla page shows the bearing-from-north
presentation rather than the live "facing" one. That is a real state the app has, on a
watch whose compass is unavailable, so it is honest; it is simply not the best version of
that screen. Retake it on real hardware if that ever becomes possible.
